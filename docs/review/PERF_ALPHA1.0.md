# Round-7: GC 強化と性能改善（計測にもとづく最適化）

## 1. 何が遅かったのか（実測）

`benchmarks/bench_alpha10.py`（ループ加算・while・fib・内包表記・join・dict・
クラスメソッド・ジェネレータ・format の 9 種）で、CPython と生成 C
（`-O2`、ランタイムも `-O2`）を比較した。

| 実装 | 実行時間（9 種合計） | CPython 比 |
|---|---|---|
| CPython 3 | 0.73 s | 1.0× |
| 生成 C（Round-6 まで） | 4.62 s | 約 6.3× 遅い |
| 生成 C（Round-7 の最適化後） | **約 3.0 s** | 約 4.1× 遅い |

`gprof`（`-pg`）による初期プロファイルでは **`p2c_gc_collect` が 47%**、
次いで `p2c_obj_new`（24.6M 回）・`gc_free_obj_data`・`p2c_heap_platform`・
`gc_mark_push` が上位を占めた。

## 2. 実施した最適化（すべて A/B 計測で効果を確認）

| 最適化 | 内容 | 効果 |
|---|---|---|
| **オブジェクト用フリーリスト** | `P2C_Object` は種類によらず同じ大きさなので、解放済みオブジェクトを上限付き（8192 個）で保持し、次の確保で再利用する（`obj_pool_pop`/`obj_pool_push`）。GC の sweep と破棄経路の両方が同じ入口を通る。リンク用ポインタは union 先頭へ `memcpy` で読み書きし、オブジェクトを太らせない | 確保主体のループで malloc/free をほぼ排除 |
| **反復の高速路** | 生成 C の `for` は StopIteration に備えて毎要素 `setjmp` を挟んでいた。list/tuple/str/range では例外が起きないため `p2c_iter_try_next()`（1=要素あり / 0=尽きた / -1=高速路不可）で例外経路を丸ごと回避し、-1 のときだけ従来の setjmp 経路へ落ちる | ループ・内包表記が大幅に短縮 |
| **`py2c run` の既定 `-O2`** | 以前は最適化フラグ無し（`-O0`）で生成 C をコンパイルしていた。既定を `-O2` にし、`P2C_RUN_CFLAGS` で上書き可能にした | `run` 利用時に数倍の差 |

| **増分アドレス索引** | スタックスキャン用の「アドレス→オブジェクト」表を、収集ごとに作り直すのをやめ、**確保時に挿入・sweep/破棄時にトゥームストーンで削除**する増分維持に変更（再構築はテーブル拡張時のみ）。これによりコストが O(オブジェクト数)×収集回数 から O(確保+解放) に落ちる。確保に失敗した場合は索引ごと破棄して線形探索へ安全側に落ちる | GC 自己時間（全体の約半分）を大幅削減 |

A/B 実測（同一マシン・連続実行・出力一致を確認）:

| 構成 | 実行時間 |
|---|---|
| 最適化なし（Round-6 相当） | 4.32 s / 4.54 s / 4.56 s |
| フリーリスト＋反復高速路 | 3.23 s / 3.23 s / 3.36 s |
| さらに増分アドレス索引（トゥームストーン修正後） | **2.66 s / 2.83 s / 3.00 s** |

累計で **約37%高速化**、CPython 比は約 6.3 倍 → 約 3.9 倍へ。

> 増分索引は一度セグメンテーション違反で撤回したが、原因は「トゥームストーンの
> 番兵値 `(void*)1` を候補との一致判定から除外していなかった」ことだった。
> スタック走査で語が `1` のときに番兵と一致し、アドレス 1 をオブジェクトとして
> マークしていた。除外判定を入れ、索引の寿命（終了時解放・再初期化で再作成）も
> 明示して再導入し、`test-embed-runtime` を含む全テストが通ることを確認した。

## 3. 計測して「入れなかった」最適化（無駄な複雑さを残さない）

| 検討した内容 | 判断 |
|---|---|
| プラットフォーム解決結果のキャッシュ（確保ごとの `p2c_platform_current()`/`p2c_platform_default()` 呼び出しを避ける） | A/B でキャッシュ有り 3.24〜3.34s、無し 3.07〜3.28s と**差が無い**ため**撤回**（呼び出し削減はコンパイラの最適化で既に効いており、キャッシュ用のグローバル参照が同等のコストになる） |
| **増分アドレス索引**（確保で挿入・sweep でトゥームストーン削除・拡張時のみ再構築） | ベンチマークで 3.25s → **2.66〜3.00s（約13〜15%改善）**。いったん embed 構成のクラッシュで撤回したが、原因は番兵値の一致判定（§2 の注記）と判明し、修正のうえ再導入。`p2c_runtime_shutdown()` で索引を解放し、再初期化後は先頭の確保で作り直す | GC 自己時間（全体の約半分）を削減 |
| GC しきい値の下限を 1MiB / 上限を 4MiB まで拡大 | 収集回数は減るが 1 回あたりのスイープ量が比例して増えるため**実行時間は改善しない**（むしろ 4MiB 固定では 5.26s と悪化）。元の上限式（生存集合の約 2 倍）を維持し、その根拠をコメントに残した |
| マーク処理のコールバック除去（`gc_traverse` の間接呼び出しを直接 push に展開） | 変更量が大きく（全型の走査関数）、得られる効果は 1 オブジェクト 1 間接呼び出し分にとどまるため見送り（コスト上位はオブジェクト数ではなく確保経路だった） |

## 4. GC 強化・バグ修正

| 項目 | 内容 |
|---|---|
| フリーリストの後始末 | `p2c_runtime_shutdown()` でプールを解放（LSan/リーク検査に残さない） |
| フリーリストの観測 API | `p2c_obj_pool_cached()/hits()/misses()` を追加（チューニングとテスト用） |
| しきい値の環境変数上書き | `P2C_GC_THRESHOLD`（バイト数、64KiB〜4MiB）でメモリと速度のトレードオフを調整可能（ホスト構成のみ） |
| 生成 C の品質ゲートが検出した不具合 | 高速路の導入時に `volatile` 変数への `(P2C_Object**)` キャストで `-Wcast-qual` に掛かった。non-volatile な一時変数へ受けてから `volatile` 変数へ写す形に修正（`GENERATED_CFLAGS` が実際に守っている例） |
| 出力の同一性 | すべての最適化で、ベンチマークおよび CPython 差分コンフォーマンス（868 アサーション）の出力が最適化前と完全一致することを確認 |

## 5. 再計測の方法

```sh
python3 benchmarks/bench_alpha10.py                 # CPython（time で計測）
./build/py2c benchmarks/bench_alpha10.py -o bench.c # 変換
cc -O2 -I./include bench.c src/runtime/python_code_to_c_runtime.c \
   src/common/python_code_to_c_common.c src/platform/python_code_to_c_platform.c \
   src/platform/python_code_to_c_platform_hosted.c src/platform/python_code_to_c_gui.c \
   src/modules/python_code_to_c_pygame.c -lm -o bench && time ./bench
```

`P2C_GC_THRESHOLD=1048576 ./bench` のように環境変数で GC しきい値を変えて、
メモリ消費と実行時間のバランスを確認できる。

`P2C_ALLOC_STATS=1 ./bench` を付けると、終了時に stderr へ測定用の内訳
（`p2c_obj_from_str` の呼び出し回数・オブジェクトの新規確保/再利用回数・
GC 収集回数・ピーク時のオブジェクト数）が出る。どの最適化がどの数字を
動かしたのかを確認するための観測フックで、未設定なら集計も出力も行わない。

## 7. Round-8: 不変リテラルの静的化（採用）

### ねらい

codegen は文字列リテラル（および識別子名・キーワード名・クロージャ環境のキー・
辞書リテラルのキー・`assert` のメッセージなど、内容がコンパイル時に確定する
文字列）を、**使うたびに** `p2c_obj_from_str("...")` で生成していた。これは
1 回につき「オブジェクト本体」と「文字列データ」の 2 回の確保と、GC への登録・
スイープ・解放を伴う。

Round-8 では、これらを `P2C_STATIC_STR` マクロで定義した
**共有・不変・GC 非追跡・コンテキスト非依存**の静的オブジェクト
（管理領域は `.data`、文字列は `.data` の char 配列）へ置き換えた。
同じ内容は 1 回だけ定義して共有する（＝同一リテラルの重複定義もしない）。

安全性は次の性質に依存しており、いずれもコードを確認して確定させた。

| 前提 | 確認結果 |
|---|---|
| str は不変（生成後にペイロードを書き換えない） | `v_str.data/len` への代入は生成時の 3 箇所のみ。`+=` も新オブジェクトを作る |
| 生成コードはオブジェクトのペイロードを直接書かない | codegen 内の `->u.v_*.` 代入は 0 件。書き込みはすべてランタイム関数経由 |
| 文字列ビルダがリテラルを破壊しない | 生成コードは `p2c_str_append` を発行しない（f-string は専用の `p2c_fstr_begin()` を使う） |
| GC が静的リテラルを解放しない | 追跡リスト（`gc_all`）に載らない。スイープ対象は自分のリストだけ |
| 再初期化（embed）で壊れない | ヒープにもコンテキストにも属さないため、`p2c_runtime_shutdown()` の影響を受けない |

### 計測（A/B）

比較は「同じコンパイラで生成した同じプログラムのうち、リテラル部分だけを
旧方式へ戻した版」を用意して行った（両者の差分がリテラル関連のみであることを
`diff` で確認し、非リテラル差分は 0 行）。

| 指標 | 旧（使うたび生成） | 新（静的リテラル） |
|---|---|---|
| `p2c_obj_from_str` 呼び出し（9 種ベンチ合計） | 2,060,017 | 1,860,006（**-200,011**） |
| フリーリスト再利用回数 | 24,165,537 | 23,965,552（-199,985） |
| GC 収集回数 | 11,019 | 10,923（-96） |
| 実行時間（5 回の最小 / 中央値） | 2.356 / 2.471 s | **2.247 / 2.390 s（約 3〜5% 改善）** |

> 実行時間の絶対値は計測時の負荷で 2.1〜2.5 秒の幅で動く（同条件で 2 回計測し、
> いずれも 3〜5% の改善を確認）。この 9 種ベンチは算術中心でリテラルの
> 出現頻度が低いため効果は控えめだが、確保・解放・GC 登録が消える分は
> リテラル密度の高いプログラム（文字列連結ループ・属性/辞書操作・クロージャ）で
> より大きく出る。

オブジェクトの新規確保回数はほぼ変わらない（435,974 → 435,948）。旧方式で
生成されていた一時オブジェクトは、フリーリストで再利用されていたため
「malloc は増えないが生成・初期化・GC 登録・解放の仕事は毎回発生する」状態
だった。Round-8 はこの仕事そのものを消す。

### 分かったこと（次の一手の根拠）

同じ計測から、**文字列生成の大半は codegen のリテラルではなく実行時生成**
（`str(n)`・辞書キーの組み立て・書式化。9 種ベンチで 1,860,006 回）であることが
分かった。したがって次の大きな削減対象はそこになる（下の表に追記）。

計測用の観測フック `P2C_ALLOC_STATS=1` を追加したので、次回以降も同じ手順で
「何がどれだけ減ったか」を数字で確認できる。

## 8. Round-9: ランタイムインスタンス化（埋め込み向け・性能への影響なし）

自作OS のタスクごとに 1 つの実行環境を持てるよう、ランタイムの状態を
インスタンス（コンテキスト）単位にまとめた。詳細と使い方は
`docs/spec/HOBBY_OS_EMBEDDING_ALPHA1.0.md` §5-2 を参照。

| 項目 | 内容 |
|---|---|
| インスタンスごとに分離した状態 | オブジェクトのフリーリスト（それまではプロセス全体のグローバル）、式評価スタック（二項演算・f-string。それまではスレッドローカル） |
| 追加した API | `p2c_runtime_context_create/select/current/destroy`（不透明ハンドル `struct P2C_RuntimeContext`） |
| 既に分離されていた状態 | GC（追跡リスト・ルート・しきい値）、クラス/モジュールレジストリ、サンドボックス予算、OOM ハンドラ |
| 回帰テスト | `tests/test_runtime_instances.c`（`make test-runtime-instances`）: 片方の確保・収集・destroy がもう片方に影響しないこと、`select(NULL)` で既定へ戻れることを固定 |

**性能への影響（A/B 実測）**: フリーリストと式スタックがコンテキスト経由の
アクセスになったため、確保経路に間接参照が 1 つ増えている。同じ生成 C を
コンテキスト化の前後でビルドして計測したところ、

| ビルド | 実行時間（5 回の最小 / 中央値） |
|---|---|
| コンテキスト化の前 | 2.247 / 2.390 s |
| コンテキスト化の後 | **2.133 / 2.184 s** |

で、退行は見られなかった（有意な差は計測時の負荷による揺れの範囲）。出力は
CPython と完全一致。

### 制限（意図的な設計）

- ヒープ（アロケータ）は共有ヒープ層／プラットフォーム側が持つため、
  インスタンスごとに別ヒープにしたい場合はカーネル側で
  `p2c_platform_set_allocator()` を切り替える。
- 1 インスタンス = 1 実行文脈を前提とし、同一インスタンスの複数スレッド同時利用は
  サポートしない（以前は式スタックがスレッドローカルだったが、これは
  「インスタンス分離」を優先した変更。GC 自体も単一の追跡リストを持ち、
  もともと同時利用はできなかった）。


### 回帰テスト

- `tests/test_static_literals.c`（`make test-static-literals`）: 内容・共有・
  GC 非追跡・辞書キーとしての利用・再初期化をまたぐ有効性を固定する。
  `make test` と `make test-sanitizers` の両方から実行される。
- 全テスト（`make test`）が exit 0、CPython 差分コンフォーマンスは
  868 アサーション（gnu11 と C99 の 2 構成）とも緑。

### 実装上の注意（このラウンドで踏んだ落とし穴）

- 共有表の値を「番号」として `void*` に詰める実装（`(void*)(intptr_t)id`）は、
  **フリースタンディング構成で `<stdint.h>` が無いためビルドできない**
  （`test-heap-unification` が `intptr_t undeclared` で失敗して発覚）。
  codegen ではポインタ⇔整数のキャストを使わず、名前（`char*`）を値として
  持つ形にした。`map_set_name()` と同じ流儀である。
- 生成 C の文字列データは `.rodata` ではなく**書き込み可能な配列**（`char x[] = "..."`）に
  置いている。`-Wwrite-strings` / `-Wcast-qual` 付きでビルドされる生成 C では、
  リテラルを直接 `char*` へ入れるキャストが警告になるため。




## 9. Round-10: 生の int64 演算（AOT アンボクシングの土台）

型付きローカル（int64_t）を生成する AOT アンボクシングの前提として、まず
**P2C_Object を作らずに整数演算するヘルパ**（`p2c_int_*_raw` / `p2c_int_*_obj`）を
ランタイムへ追加し、意味論を P2C_Object* 版と共有した。

| 項目 | 内容 |
|---|---|
| 追加した API | `p2c_int_{add,sub,mul,floordiv,mod,bitand,bitor,bitxor,lshift,rshift,neg,invert}_raw` と、相手が P2C_Object* の混在比較 `p2c_int_{lt,le,gt,ge,eq,ne}_obj` |
| 意味論の共有 | `//` と `%` の整数ロジックを `p2c_int_divmod_i64()` に切り出し、P2C_Object* 版と raw 版の両方が同じ関数を使う。オーバーフロー判定も既存の `p2c_int_*_checked()` を共有 |
| 回帰テスト | `tests/test_int_raw_ops.c`（`make test-int-raw-ops`）: 19 個の値（0・±1・±7・シフト境界・2^53 超・INT64_MAX/MIN）× 10 演算子を全組合せで突き合わせ、**例外が出る場合も例外名まで一致**することを確認。混在比較は int/float/bool/None/str を相手に確認 |
| 副産物 | この突き合わせが既存の不具合を検出した（`docs/review/BUGFIX_ALPHA1.0.md` §8.10: 2^53 超の整数の順序比較が double 経由で丸められ CPython と食い違っていた）。修正済み |
| 現状 | ヘルパは用意済みだが、**codegen 側の型付きローカル生成はまだ未実装**（次の段階）。したがって既定の生成コードと性能は変わらない |

### 次の段階（未着手）

codegen に「int しか入らないと証明できたローカル」を `int64_t` で宣言する解析を入れ、
代入・複合代入・比較・算術を生経路へ置き換える。安全側の設計として:

- 解析は関数単位の**前処理パス**（代入の型が確定してから宣言・本体を出す）にする。
  解析で「int 以外の代入がある」「クロージャに捕捉される」「タプル展開・for・with・
  except の対象になる」「global/nonlocal 宣言がある」場合は型付きにしない（保守的）。
- 読み出しは既定でボックス化（`p2c_obj_from_int(x)`）し、算術・比較・複合代入など
  「生で使える箇所」だけ生経路にする。型が合わない出力は生成 C が
  **コンパイルエラーになる**ので、取りこぼしは静かな誤動作ではなく即座に検出できる。
- オプション（`--unbox` 相当）で切り替えられるようにし、全テストと計測が
  緑になった時点で既定 ON にする。
