# Python Code to C Alpha1.0 — 品質基準線監査

## 結論

既存の `tests/complex_alpha10.py` は60個の関数を持っていたものの、従来の実行スクリプトは戻り値の内容を検査せず、最後に表示される件数 `60` だけを確認していた。この方式では、個別ケースの意味論が壊れても件数さえ維持されれば成功となるため、品質ゲートとして不十分であった。

この監査で複雑コーパスを **CPython差分テスト**へ転換した。現在は同じPython入力をCPythonとAlpha1.0生成Cで実行し、60行の実値出力を `diff -u` で比較する。辞書キーviewの処理系固有表現は、キー列という意味論を保つ `list(d.keys())` に正規化し、誤検知を避けた。

## 現行テスト資産の評価

| 資産 | 現在の強み | 監査で確認した不足 |
|---|---|---|
| `complex_alpha10.py` | 算術、文字列、コンテナ、制御、関数、例外、クラスを横断する60ケース | ケースID・機能要件・障害モード・期待意味が外部から追跡できない。1ファイルに集約され、失敗原因の局所化が弱い |
| `audit_regression.sh` | 短絡評価、loop-else、with、複合代入、削除、ビット演算、厳格C11の診断を検査 | 実行対象が限定的で、各テストのカバレッジ台帳がない |
| `set_regression.sh` | set、set内包表記、frozensetフォールバックをCPython差分で検査 | setメソッド、例外契約、反復中変更など未検査 |
| `test_gc_gui.c` | GCルートとGUIコマンドバッファを直接Cで検査 | 生成プログラムのGCストレス、容量境界、エラー復帰を系統的に検査していない |
| `smoke.sh` | 代表例が実行できることを確認 | CPython出力との比較ではなく、実例ごとの機能意図が明文化されていない |

## 再設計の品質原則

新しいコーパスでは、テストケースを「任意の60個」ではなく、**実装上の失敗モードに一対一または少数対一で対応する仕様証拠**として扱う。各ケースには固定ID、対象機能、前提条件、期待出力、検証方法、失敗時に疑う層を与える。

| 原則 | 適用方法 |
|---|---|
| 意味論中心 | 件数やクラッシュ有無ではなく、CPythonとの差分、期待診断、またはC APIの不変条件で判定する |
| 独立性 | 1ケースは1つの主張を担当し、失敗した機能層を識別できるようにする |
| 正規化 | set順序・objectアドレスのようにPython仕様が順序や表現を保証しない値は、意味を失わない範囲で正規化する |
| 層別検証 | 変換器、生成C、ランタイム、GC、GUI、strict C11、freestandingを別々に検証する |
| 回帰可能性 | 新たに修正した不具合は必ず再現ケースを追加し、既知制限は通過と誤認されない期待診断として固定する |
| 移植性 | 通常生成、strict ISO C11生成、freestandingコンパイラコアを別の契約としてテストする |

## 優先テスト領域

次段階では、機能群ごとに明確な目的を持つ80件以上のケースを作る。最優先は、評価順序・例外掃除・スコープ・アンパック・複合代入・コンテナ変異・反復のように、生成Cの静的な見た目だけでは正しさを保証できない領域である。

> 60件という数値は目標ではなく下限とする。追加するケースは、対応構文、修正済み不具合、移植性契約、または過去に誤実装となり得た意味論のいずれかを検証できる場合に限る。
